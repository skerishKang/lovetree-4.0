## 2. 예상하는 제품의 성장

핵심 순환은 **내 순간 기록 → 마음의 연결 → 다시 감상 → 선택한 경로 공유 → 다른 팬의 감상 → 자기 순간 기록**이다.
화면 수가 아니라 이 순환의 성공이 기준이다. 커뮤니티는 공개된 트리와 순간을 매개로 시작하는 안을 권장한다. 일반 자유게시판·DM은 실제 필요가 확인된 후 별도 판단한다.

| 단계 | 사용자에게 제공할 경험 | 필요한 기반 / 기존 이슈 |
| --- | --- | --- |
| A. 개인 기록 안정화 | 로그인·재방문·기기 간 복원·충돌 안내 | #13·#57·#64, 실제 운영 인증/DB 확인 |
| B. 화면 연결 기반 | 같은 트리/선택을 여러 표현으로 보기 | #65·#9, 기존 세 화면 계약 통일 |
| C. 실제 미디어 기록 | URL·영상 시점·썸네일·선택 사진 | #14, 기존 파서/입력 재사용·보존 계약 |
| D. 선택적 공유·감상 | 공개/링크 범위를 선택하고 읽기 전용 링크 열기 | #15, 서버 권한·비공개 필드 제외 |
| E. 발견형 커뮤니티 | 대상/감정별 공개 트리 탐색·프로필·즐겨찾기 | #15, 페이지네이션·공개 색인·캐시 |
| F. 상호작용 | 반응·댓글·신고·차단·알림 | #15, 운영자 처리·스팸/중복 방지 |
| G. 경로 전파 | 남의 공개 순간을 출처와 함께 내 기록으로 채택 | #15, 새 ID·원본 불변·공개 대상만 복사 |
| H. 선택 고도화 | AI 연결 제안·회고/코스·공식 큐레이션 | 별도 제안. 실제 수요와 권한/비용 검증 후 |

B와 C는 필요한 계약을 먼저 맞춘 뒤 일부 병행할 수 있다. 모든 B 구조 작업을 끝낼 때까지 사용자 기능을 무조건 막는 순차 게이트로 쓰지 않는다. 가격·랭킹·공식 배지·기획사 제휴·모바일 앱 일정은 미확정이다.

## 3. 리모네의 수십 화면을 연결하는 방법

기존 리모네의 Product Core / Experience Capabilities / Scenario Variants 구분을 4.0에 맞게 활용한다.

1. **공통 제품 기능**: 신원/소유권, Tree/Moment/연결, 저장·동기화, 미디어, 공유·커뮤니티.
2. **공통 조작·연출**: 선택/경로 탐색, 모달, 책 넘김, 궤도, 타임라인, 공간 지도.
3. **화면**: 공통 데이터와 조작을 사용하는 궤도/책장/기억책/보드/새 후보.

각 원본을 다음으로 분류한다.
- 같은 일을 다른 모양으로 표현: 기존 보기의 시각 변형 후보.
- 여러 화면이 공유할 효과/조작: 재사용 기능으로 추출.
- 기존에 없는 사용자 과업: 신규 기능으로 정의.
- 예시 데이터만 있는 화면: 데이터 어댑터가 필요한 원본.
- 모바일·초점·성능이 미검증인 화면: 후보로 보존하고 완료로 표시하지 않음.

사용자 메뉴에 원본 30개를 그대로 나열하지 않는다. 기록/내 트리/감상/발견처럼 사용자 목적을 우선하고, 감상 안에서 보기 방식을 선택한다.

## 4. 최소 화면 계약

예시 계약이며 구현에서 불필요한 추상화는 줄인다.

- 등록 정보: id, route, 목적, 필요한 데이터, 지원하는 읽기/편집 동작, 모듈 로더.
- 입력 context: treeId, momentId, 읽기 전용 여부, 검증된 snapshot/selectors.
- 행동: selectMoment, navigate, add/edit 요청 등 공통 actions.
- lifecycle: mount(host, context), 필요한 경우 update(context), dispose().
- 저장은 공통 명령/검증 경계를 통한다. 뷰마다 localStorage/API 쓰기를 만들지 않는다.
- 직접 URL·새로고침·뒤로가기·읽던 위치를 한 라우팅/선택 규칙으로 처리한다.
- dispose는 이벤트·RAF·observer·미완료 요청을 정리한다. 이전 계정/세대 응답은 폐기한다.
- shell은 메뉴·로그인/동기화 상태·모달·여백을 소유한다. 뷰는 다른 뷰의 DOM을 조작하지 않는다.
- 공개 읽기 모드의 편집 버튼 숨김은 UX일 뿐이다. 서버가 실제 소유권과 공개 범위를 검사한다.

기존 hash URL·저장 형식·예시 읽기 전용·입력 보호를 유지하면서 작은 PR로 추출한다. main.js 줄 수 자체보다 책임 분리가 목표다. 프레임워크 전면 교체나 마이크로서비스 전환은 전제가 아니다.

## 5. 공통 데이터와 커뮤니티 확장

원본 순간, 사용자가 확인한 연결, 화면 배치/읽던 위치, 파생 검색/추천 정보는 책임을 구분한다.
- 기존 parentId(부모 하나)와 links(관련 순간)를 먼저 유지한다. 다중 부모는 경로·삭제·읽기 순서까지 따로 결정한다.
- 미디어는 원본 URL·종류·시점·저장 파일 참조 등 필요한 필드를 버전 있는 변환으로 추가한다. validateState·백업·import·sync 왕복을 함께 보완한다.
- 개인 전체 workspace 문서 CAS는 초기 편집/동기화에 유지할 수 있다. 커뮤니티는 다른 사람의 private workspace를 내려받아 브라우저에서 거르는 방식으로 만들지 않는다.
- 공개 읽기는 서버가 허용된 데이터만 반환하는 별도 조회/공개 projection과 페이지네이션으로 시작한다. 전체 테이블 구조를 당장 다시 쓰지는 않는다.
- 공개 취소/순간 삭제 시 공개 검색·카드·캐시에서도 회수되도록 한다.
- 반응·댓글·조회는 개인 workspace JSON에 전부 넣지 않는다. 별도 소셜 레코드로 멱등·동시성·대상 접근 검증을 둔다.
- 다른 팬의 순간 채택은 동기화와 다른 동작이다. 새 ID와 출처를 남기고 원본을 바꾸지 않는다. 공개·복사 허용 범위는 별도 결정한다.
- 전체 문서 쓰기 비용/충돌·기록 규모가 실제로 한계에 닿으면 저장 API를 부분 수정 방식으로 발전시킨다. 현재 300순간 상한 시험만으로 수천 순간 성능을 보증하지 않는다.
- 공개 카드 목록을 가져온 뒤 카드마다 순간 전체를 요청하는 N+1 패턴은 그대로 승계하지 않고 서버 요약 응답을 검토한다.

## 6. 운영 준비와 제안 결정 목록

기능 구현과 운영 적용을 구분한다. 현재 우선은 #64 남은 UI/API 응답 경계 수정과 운영 인증 연결이다.
커뮤니티를 켜기 전 필요한 것은 공개 읽기 계약, 실제 운영 소유권 검증, 백업/복원과 삭제 회수, 댓글 등 쓰기에 맞는 신고/차단/운영 처리다. 별도 대규모 관리 플랫폼부터 만들지는 않는다.
컴2 운영은 프로세스 재시작·DB 백업/복원·장애 시 로컬 기록 보존·외부 진입 경로를 확인한다. 기존 런북을 활용하고 중복 문서 체계를 만들지 않는다.

Owner 검토가 필요한 향후 제품 제안:
1. 새 기록의 기본 공개 범위와 공개 전환 UX.
2. 커뮤니티 첫 버전의 범위: 공개 트리 감상·대상별 발견을 우선할지.
3. 일부 순간/메모 공개 여부와 내 트리로 채택할 때 출처·허용 범위.
4. 알림·AI 제안·요금·공식 큐레이터/기획사 기능의 도입 시점.
이 문서는 이를 확정하지 않는다.

## 7. 바로 다음 구조 작업의 완료 기준

- 기존 궤도/책장/기억책을 같은 계약으로 연결하고 외형은 보존한다.
- 신규 원본 한 개를 기존 공통 데이터로 표시하고 편집/선택/읽기 모드 경계를 검증한다.
- 화면 전환·계정 전환 후 이벤트/선택/응답이 남지 않는다.
- 모바일/PC·긴 상태 문구·팝업에서 공통 바가 주요 행동을 가리지 않는다.
- 새 화면을 위해 로그인·저장·메뉴 체계를 복제하지 않는다.
- PR에 기존 출처·재사용/미이식 이유를 기록한다.
