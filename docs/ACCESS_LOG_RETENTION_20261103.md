`lovetree_request_claims` is request-idempotency metadata. Removing an old claim ends replay lookup for that client key after the retention window; the normal workspace revision check still guards stale writes. Account deletion may remove a user's request claims earlier through its existing deletion path, while its hashed deletion record keeps its own bounded retention (90 days, see the 2026-11-16 row above).

## Cleanup and schedule

`server/db/access-log-retention-postgres.js` deletes rows at or before the UTC cutoff (`now - 90 days`) from the three allow-listed operational tables. Each statement uses an ordered `FOR UPDATE SKIP LOCKED` batch. Defaults cap a run at 500 rows × 4 batches per table. The systemd timer (`deploy/host-com2/lovetree-api/lovetree-log-retention.timer`) fires daily at `03:17:00` with `RandomizedDelaySec=15m` and `Persistent=true`, adding a randomized delay and persistent catch-up. The result log contains only cutoff time and deleted row counts. The same job also deletes expired guest feedback (replies first, then posts) and expired account-deletion records; those counts are logged as `guestFeedback.replies`/`guestFeedback.posts`/`accountDeletions`.

The deployment installer places the oneshot and timer units after an explicitly requested install, and does not start or enable them. The timer must be enabled by a separately authorized server operator. `journald-retention.conf.example` is host-wide and is not installed by the Lovetree installer. Nothing in this change has been applied to a server or Cloudflare account.
