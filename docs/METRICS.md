# 러브트리 4.1 숫자 기준

둘러보기와 첫 화면에 보이는 숫자가 무엇을 세는지, 그리고 아직 정해지지 않은 것을 구분한다. 이 문서는 현재 구현을 기록한 것이며 코드 변경을 수반하지 않는다.

## 지금 4.1에 있는 숫자

| 이름 | 보이는 곳 | 무엇을 세나 |
|---|---|---|
| 담긴 수(즐겨찾기) | 둘러보기 카드 `즐겨찾기 N` |active 공개 트리를 즐겨찾기한 로그인 주체의 수를 `lovetree_community_favorites` 행으로 센다. 같은 주체가 같은 공개 트리를 두 번 담아도 행은 하나다(중복 키 제약 + `ON CONFLICT DO NOTHING`). 쓰기는 로그인 후에만 되고, 읽기는 로그인 없이도 된다. |
| 공감 수 | 둘러보기 카드 `공감 N`, 반응 버튼 | `lovetree_community_reactions` 행을 공개 트리·종류별로 센다. 종류는 공감·좋아요·사랑·웃음·놀람·슬픔·화남 일곱 가지이고, 같은 주체가 같은 공개 트리에 같은 종류를 두 번 남겨도 행은 하나다. 값이 0이고 내 반응도 없으면 그 종류 버튼은 숨는다. |
| 댓글 수 | 서버 `stats.comments`, 펼침 안 댓글 목록 | 공개 트리에 달린 `status='visible'` 댓글 행 수다. 카드에는 표시하지 않고 상세 펼침에서 목록으로 보여 준다. |
| 공개 집계 수 | 첫 화면 정보 줄 `순간 N`·`트리 N` | 로그인 없이 읽을 수 있는 공개 집계다. 공개 상태이고 순간이 3개 이상인 트리와 그 순간 수를 세며, 서버가 1분 메모리 캐시를 두고 응답에도 60초 캐시를 실어 같은 한도로 재활용한다. |
| 내 순간 수 | 첫 화면 정보 줄 `모아둔 N`·`전체 N`, 서재 `순간 N` | 로그인한 사람의 workspace 문서에서 모아둔 순간과 전체 순간을 각각 센다. 공개 집계와 섞지 않는다. |

### 같은 사람 중복과 몰표 방지

- 즐겨찾기·반응·댓글·신고는 로그인 주체(`subjectId`)를 키로 쓴다. 원본 주소·기기 정보를 공개 수에 넣지 않는다.
- 같은 주체가 같은 대상에 같은 동작을 반복해도 저장 행은 하나다(유일 제약 + 충돌 무시).
- 쓰기 요청은 주체와 동작 종류별로 1분당 횟수를 제한한다(즐겨찾기·반응 40회, 댓글 12회, 신고 6회). 추가로 댓글·신고는 클라이언트 키를 받아 되풀이 제출을 막는다.
- 차단한 공개자에게는 반응·댓글 쓰기를 막는다. 신고 접수만으로 공개 트리를 자동 숨기지 않고 운영 검토 후 명시적으로 숨긴다.

### 공개 범위

- 숫자는 공개 상태인 공개 트리에만 붙는다. 비공개 트리·소유자 전용 화면의 값은 공개 응답에 나가지 않는다.
- 발견 목록과 검색에는 소유자가 발견에 공개하는 데 동의한 트리만 오른다. 공개 링크를 만들었다고 자동으로 발견에 나오지는 않는다.
- 운영에서 숨긴 공개 트리와 내가 차단한 공개자의 트리는 목록에서 빠진다. 공유 링크를 직접 연 경우는 읽기 전용으로 그대로 볼 수 있다.
- 공개한 사람의 기록은 개인 workspace와 분리된 표에 저장하고, 공개 응답에는 집계 수만 내보낸다. 계정 식별자는 노출하지 않는다.

### AI 테스터와 시험 계정

- AI 테스터의 공개 트리는 카드에 `AI 명예회원` 배지를 따로 달고, 배지 외에는 같은 카드 형태로 보여 준다.
- 시험 계정 역할의 트리는 발견 목록·검색에서 제외한다. 공유 링크를 직접 여는 것은 그대로 된다.
- 현재 집계 수에는 배지가 붙은 트리의 즐겨찾기·반응·댓글도 함께 들어간다. 이 값을 순위나 추천에 쓸 때 어떻게 다룰지는 아직 정해지지 않았다.

### 고객이 적을 때

- 현재는 수가 작아도 숫자를 그대로 보여 준다. 즐겨찾기는 0이어도 `즐겨찾기 0`이 보이고, 반응은 0이면 버튼이 숨는다. 같은 화면에서 0의 노출 기준이 다르다.
- 첫 화면 공개 집계가 0이면 `0`을 보여 주고, 공개 트리가 없으면 안내 문구로 대신한다. 작은 수를 숨길지, 0으로 표시할지, 기준치를 둘지는 정해지지 않았다.

## 지금 4.1에 없는 것

아래는 현재 화면·서버에 없으므로 "현재" 숫자로 취급하지 않는다. 각 항목이 필요해질 때 별도 결정과 구현이 필요하다.

- **랭킹(#760)**: 인기 점수·순위가 없다. 둘러보기 정렬은 마지막 활동(보이는 댓글이 있으면 그 시각, 없으면 공개 시각)이 최신인 순서이고, 화면 문구도 "새로 공개된 순서예요"라고만 말한다. 담긴 수·공감 수·최신 활동 중 무엇을 점수로 삼을지 정해지지 않았다. 공개 순간 수를 그대로 "인기"라고 부르지 않는다.
- **추천(#818)**: 추천 신호·개인화 점수가 없다. 무엇을 근거로 추천할지, 로그인 여부에 따라 달리할지 정해지지 않았다.
- **많이 담은 구간(#792 4단계)**: 순간의 시작·끝 초는 저장하지만 구간별 담기 수를 세지 않는다. 구간을 무엇으로 묶고 어디에 표시할지 정해지지 않았다.
- **조회 수**: 트리 단위 조회 수가 없다. 목록을 불러오거나 카드를 스크롤한 것만으로 수를 올리지 않고, 값이 없는데 `0`이라고 보여 주지도 않는다.
- **이번 주**: 7일 또는 특정 기간으로 묶은 집계가 없다. "이번 주"라는 말은 화면에 쓰지 않는다.

## 대표 결정 필요

1. 랭킹(#760)에서 "인기"의 정의: 담긴 수, 공감 수, 최근 활동, 조회 수, 또는 혼합 중 무엇인가. 순간 수를 인기의 근거로 쓸 수 있는가.
2. 둘러보기에 정렬 선택지를 추가한다면, 현재 "새로 공개된 순서"를 유지하면서 라벨을 어떻게 붙일 것인가.
3. 조회 수를 도입한다면 집계 단위(공개 트리 상세 열기 등), 같은 사람 중복 기간, 로그인 없이 센 값의 신뢰도 기준은 무엇인가.
4. "이번 주"가 필요해지면 기간 길이(7일 등), 기준 시간대, 시작·끝 경계, 과거 주수를 어떻게 표기할 것인가.
5. AI 명예회원 기록을 숫자와 순위에 포함할 것인가. 포함한다면 배지와 분리 표시를 어떻게 할 것인가.
6. 댓글 수를 카드에도 표시할 것인가, 현재처럼 펼침에만 둘 것인가.
7. 고객이 적을 때 숫자 노출 기준: 0 표시, 숨김, 또는 최소 기준치를 둘 것인가. 즐겨찾기·반응의 서로 다른 0 처리 방식을 통일할 것인가.
8. 몰표 방지 기준: 주체당 1회 영구 중복 제거로 충분한가, 기간제 중복 허용이 필요한가, 요청 제한 값은 무엇인가.
9. 많이 담은 구간(#792 4단계)의 "구간" 범위와 집계 주체, 표시 위치는 무엇인가.
