# 전시 보기 설계 — 시안 62 기억조각상 원형 레일 전시 (#1425)

트리 하나를 전시처럼, 순간 하나를 전시물 하나로 넘겨 보는 **트리 보기의 새 모드 '전시'**의 설계와 시제품 기록이다.
이번 단계는 설계 문서와 시제품(초안 PR)까지다. 병합·운영 반영은 하지 않는다.

- 기준: `main` 901136f3
- 시제품: `public/v41/views/exhibit/` (새 파일 4개) + 개발용 진입 한 곳(`public/v41/shell/navigation.mjs`)
- 여는 법: 로그인한 뒤 주소에 `?view=exhibit` 를 붙이고(`/v41/?view=exhibit`) 트리 탭을 연다. 보기 고르기 메뉴에는 넣지 않았다.
- 비교용 개발 값: `&order=date`(날짜 차례), `&mono=off`(사진 흑백 끄기)

판단이 갈리는 곳은 정하지 않고 **선택지**로 적었다. 한데 모은 목록은 10장에 있다.

## 1. 시안 분해

확인한 원본은 시안 62 버전 1.1(조각상 다양화·미디어 뷰어·메뉴 기능 후보)의 `현재후보.html` 이다(20,728,647바이트, sha256 `bc5484a1c545…`).

### 차례 — 선택지

| | 방식 | 좋은 점 | 아쉬운 점 |
|---|---|---|---|
| 가 | **트리 차례**: 시작 순간에서 먼저 이어진 길을 끝까지 간 뒤, 가까운 갈림으로 돌아와 잇는다 | 트리·책에서 읽는 길과 같다. '이어진 이유'가 앞 장면과 맞물린다. 순간을 더해도 앞쪽 번호가 흔들리지 않는다 | 갈림으로 돌아올 때 날짜가 거꾸로 갈 수 있다 |
| 나 | **날짜 차례**: 순간 날짜가 이른 것부터(같은 날은 만든 차례, 날짜 없는 것은 맨 뒤) | 시간 흐름이 한눈에 보인다 | 갈림이 섞여 '이어진 이유'가 앞 장면과 무관해진다. 날짜를 고치면 번호가 바뀐다. 날짜 없는 순간이 뒤로 몰린다 |
| 다 | **고른 순간만**: 사용자가 대표 순간(예: 7개)을 고른다 | 시안과 가장 가깝다(7장면). 공유·자랑에 알맞다 | 고르는 화면과 저장 자리가 새로 필요하다 |

- 시제품은 **가**를 기본으로 하고 `?order=date` 로 **나**를 볼 수 있게 했다. 나무를 엮는 일은 트리 보기의 `buildHierarchy` 를 그대로 썼다(깨진 기록도 순간을 잃지 않는다).
- 시험용 서른 개 트리(줄기 12 + 갈림 4곳)에서 두 차례는 30자리 가운데 30자리가 달랐다. 예를 들어 줄기 3번째에서 갈린 네 순간은 트리 차례로는 24~27번째, 날짜 차례로는 5·6·8·9번째다(시험 자료는 일부러 갈림의 날짜를 앞쪽으로 넣었다).
- 권고는 **지금 보기(트리 화면의 모드)는 가**, **공유 페이지 전시 모드(이슈 2단계)는 다**다. 정하는 것은 대표 결정으로 남긴다.

### 제목·날짜·마음 한마디

| 설정 | 값 | 전시 보기에서 |
|---|---|---|
| 제목 표시(`titleDisplay`) | 둘 다 | 큰 제목 = 내 제목(없으면 영상 제목), 바로 아래 작은 줄 = 영상 제목(둘 다 있을 때만) |
| | 내 제목 | 큰 제목 = 내 제목(없으면 영상 제목), 작은 줄 없음 |
| | 영상 제목 | 큰 제목 = 영상 제목(없으면 내 제목), 작은 줄 없음 |
| 날짜 표시(`dateStyle`) | 점·줄표·긴 표기 | 번호 옆(`01 · 2026. 01. 06` / `01 · 2026-01-06` / `01 · 1월 6일`)과 상세 판 윗줄 |

- 두 설정 모두 다른 화면과 같은 함수(`titleView`, `formatDisplayDate`)를 쓰고, 셸이 보내는 설정 메시지를 받으면 열린 채로 다시 그린다(시제품에서 세 값씩 확인).
- **마음 한마디**는 시안의 '설명 한 줄' 자리에 둔다(14px, 두 줄까지). 전체 글은 순간 상세의 '마음 한마디' 칸에 있다. 썸네일이 없는 순간은 종이 한 장에 마음 한마디를 크게 적어 작품으로 걸고, 옆 설명 줄은 겹치지 않게 뺀다. 낮은 창(휴대폰 가로)에서는 설명 줄을 숨기고 상세에서만 보인다.
- **감정**은 뒤 큰 낱말과 강조 원 색으로 보인다. 큰 낱말은 장식이라 글자 노드가 아니라 CSS 생성 글자로 그렸다(읽어 주기에서는 장면 이름에 감정이 들어 있다).
- **이어진 이유**는 순간 상세에 '‘부모 순간 제목’에서 — 이유'로 적는다.
- 레일 이름표를 제목으로 할지는 선택지다 — 제목(시제품) / 날짜 / 번호만. 제목은 알아보기 쉽지만 길면 잘린다(이웃 사이 폭에 맞춰 말줄임).

### 썸네일 고르기

- 공용 차례(`thumbnailCandidates` → `nextThumbnailStep`)를 그대로 쓰되, 크게 보이는 자리라 맨 앞에 큰 그림을 하나 더 둔다: 가로 영상 `maxresdefault`, 세로 영상 `oardefault`. 없거나 회색 자리 그림이면 저장된 썸네일 → `hqdefault` → `mqdefault` 로 내려가고, 모두 실패하면 글 전시물로 바꾼다.
- **자동 표시 규칙(#327)** 때문에 유튜브 썸네일은 내 기록에서만 처음부터 보인다. 공유 감상·예시에서는 바깥 요청을 하지 않으므로 영상 순간이 모두 글 전시물이 된다. 공유 페이지 전시 모드를 하려면 이 규칙을 어떻게 할지 먼저 정해야 한다(10장 5번).

### 'exhibit' 를 넣는 방법 — 선택지

| | 방법 | 바뀌는 곳 | 평가 |
|---|---|---|---|
| A | **트리 화면 안의 보기 모드** — 도구 줄에 '나무 · 전시' 두 칸, 고른 값은 계정 설정(`prefs.treeView`)과 기기 미러에 저장(서재의 선반·회전과 같은 길) | 트리 화면 HTML·도구 줄, 설정 저장 길. 서버 값 목록은 그대로 | 이슈가 말한 '트리 보기의 새 모드'에 맞다. 서버·배포 순서 걱정이 없다. 트리마다 다르게 둘 수는 없다 |
| B | **열 화면 값에 'exhibit' 추가** — 트리마다 저장 | `TREE_OPEN_VIEWS`, 화면 목록, 트리 관리 창의 고르기, 서버 검증(같은 파일) | 트리마다 '전시로 열기'를 정할 수 있고 공유 링크도 전시로 열 수 있다. 서버가 먼저 새 값을 알아야 해서 배포 순서를 지켜야 한다(옛 서버는 모르는 값을 tree 로 되돌린다) |
| C | **독립 화면** — 머리줄에 탭 추가 | 머리줄, 화면 목록, 주소 | 탭이 하나 늘어 머리줄이 좁아진다. 트리 화면과 겹친다 |

- 권고: **A 로 시작**하고, 공유 페이지 전시 모드를 할 때 **B 를 얹는다**(공유 링크가 가리키는 화면 값이 필요해지는 때).
- A 로 갈 때 트리 화면은 지금 한 파일(`tree.js`)이라 보기 틀이 없다. 서재처럼 `tree-views.mjs`(나무·전시)를 두고 같은 약속(붙이기·배치·이동·정리)을 따르게 옮기는 일이 먼저다. 시제품은 그 약속에 맞춰 써 두었다(아래 표).

### 시제품의 진입

- `navigation.mjs` 의 `screenUrl` 한 곳에서, 셸 주소에 `?view=exhibit` 가 있을 때만 트리 화면 자리에 `views/exhibit/exhibit.html` 을 띄운다.
- 셸은 계속 '트리' 화면으로 다룬다. 그래서 머리줄 탭·주소(`#my/tree?…`)·테마·트리 고르기·휴대폰 ＋ 단추 자리가 트리 화면과 같다. 화면 목록·메뉴·저장값은 건드리지 않았다.
- 기존 화면 파일은 고치지 않았다.

### 보기 약속(#1375·#1376)에 대응

| 약속 | 전시 보기 |
|---|---|
| 입력: 순간·트리 자료 | `LTDEMO.moments`·`edges`·`prefs` 만 읽는다 |

### 머리줄·도구 줄과의 관계

- **머리줄**: 셸 것 그대로. 시안의 상표·위 메뉴는 가져오지 않는다.
- **도구 줄**: 공용 부품(`mountScreenToolbar`)을 트리 화면과 같은 모양으로 쓴다. 왼쪽은 트리 고르기(남의 트리·예시는 이름표), 오른쪽은 `← 01 / 05 →`.
- 시안의 쪽 번호(오른쪽 위)는 도구 줄 오른쪽으로, 판 이름 줄(전시 이름)은 트리 고르기 이름으로 갔다. 그래서 무대 안에는 레일·작품·글·안내·진행 선만 남는다.
- 모드 전환 두 칸('나무 · 전시')은 A 로 정해지면 도구 줄 오른쪽 맨 앞에 둔다(공용 두 칸 전환 모양).

## 6. 접근성

| 기준 | 시제품 실측(56개 상태: 390·844×390·1440·2560 × 밤·정원 × 순간 1·5·30과 종류별 장면·상세) |
|---|---|
| 누름 44px | 가장 작은 누름 영역 44px(레일 점·순간 보기·작품·상세 단추·닫기). 도구 줄 단추는 공용 규칙대로 보이는 높이 36px + 위로 넓힌 영역 |
| 글자 12px 이상 | 가장 작은 글자 12px |
| 대비 4.5:1 | 가장 낮은 값 5.31:1(정원의 옅은 글자) |
| 겹침·가로 넘침 | 0 (공용 화면 검사기 + 작품·글·레일 이름표·안내·진행 선·셸 ＋ 단추 겹침 검사) |

- **움직임 줄이기**: 기기 설정(`prefers-reduced-motion`)과 러브트리 설정의 '움직임 멈춤'(셸 메시지) 둘 다 따른다. 켜지면 넘김이 같은 순간에 바로 바뀌고(중간 프레임 없음) 그림이 서서히 나타나는 효과도 끈다. 끌기는 손을 따라오되 놓으면 바로 선다.

- **초점 표시**: 포인트 색 2px 테(밤 금색 10.49:1, 정원 장미 5.10:1).

## 7. 유튜브 임베드 규정 (#1354·#1378)

- **플레이어 위에 우리 요소를 얹지 않는다.** 전시 보기에는 플레이어가 없다. 장면과 순간 상세에는 썸네일 그림만 있고, '재생'을 누르면 상세 판을 닫고 공용 크게 보기로 넘긴다. 시제품에서 플레이어 9지점의 맨 위 요소가 모두 플레이어였고(가림 0), 크기는 1440에서 1310×737, 390에서 365×205(200×200 이상), 자동 재생 플레이어는 1개였다. 크게 보기를 닫으면 플레이어도 사라진다.
- 재생할 수 없는 영상(삭제·비공개·임베드 금지)은 공용 크게 보기가 플레이어를 걷고 안내로 바꾼다(기존 동작 그대로).
- **썸네일은 그대로 보여 준다**(이슈 본문 규칙). 흑백·가장자리 흐림·배경 지우기·덮어 그리기를 하지 않는다. 재생 표시도 썸네일 위에 그리지 않고 글 칸의 '순간 보기'로 뺐다. 꾸밈은 썸네일 바깥에만 둔다 — 가는 틀, 여백, 받침 그림자, 뒤 큰 낱말.
- 4:3 썸네일(`hqdefault`)의 위아래 검은 띠는 16:9 틀에 맞춰 잘려 보이지 않는다. 그림을 바꾸는 것이 아니라 다른 화면 카드와 같은 맞춤(`object-fit: cover`)이다.
- **흑백은 사용자가 올린 사진에만** 건다(같은 출처의 내 보관 사진·예시 그림). 순간 상세에서는 흑백을 35%로 낮춰 색이 돌아온다.
- 썸네일 대표 색으로 바탕을 물들이는 안(이슈 본문)은 하지 않았다. 그림 화소를 읽어야 해서 따로 확인이 필요하다.

## 9. 시제품 결과

### 확인한 것

- 실제 길로 확인: 가짜 작업 자료 → 셸(로그인 상태) → 트리 화면 자리의 전시 보기. 시험 트리 세 벌(순간 1·5·30)에 유튜브 가로(큰 썸네일 있음·작은 썸네일만), 유튜브 세로, 올린 사진, 썸네일 없음(글), 긴 제목을 섞었다.
- 썸네일은 **대역 그림**이다. 유튜브 그림 주소 요청을 저장소 안 예시 그림으로 응답했다 — `hqdefault` 는 480×360(위아래 띠 포함), 세로 원본 비율은 405×720, 큰 썸네일은 벡터 그림을 1280×720 으로 그린 것, 없는 그림은 404와 120×90 회색. 실제 유튜브 그림은 캡처에 넣지 않았다.
- 캡처: 본 대상 12장(390×844·1440×900 × 밤·정원 × 순간 1·5·30) + 종류별 16장 + 순간 상세 4장 + 844×390·2560×1440 10장 + 넘기는 중 1장. `lovetree-sc` 의 `design-review/1425/` 아래 커밋 이름 폴더에 있다(PR 본문에 주소).

### 움직임 측정(헤드리스 PC 크롬, 서른 개 트리를 한 장씩 29번 넘김)

| 조건 | 평균 프레임 간격 | 95% | 최대 | 34ms 넘는 프레임 |
|---|---|---|---|---|
| 1440×900 | 16.64ms | 16.8ms | 16.8ms | 0 / 471 |
| 390×844 | 16.65ms | 16.8ms | 16.8ms | 0 / 468 |
| 390×844, CPU 4배 느리게 | 18.18ms | 33.3ms | 83.4ms | 8 / 586 |

- 느리게 건 값은 잴 때마다 흔들린다(같은 PC에서 다른 작업이 함께 돈다). 한 번 더 쟀을 때는 4배 0개, 6배 14개였다.

- 손가락 입력은 헤드리스 크롬의 입력 흉내로 봤다(밀기 한 장씩, 위아래 손짓은 넘기지 않음, 새 화면에서 작품 누르기). 이 흉내에서는 한 번 끈 뒤의 누르기가 `click` 을 만들지 않았는데, 지금의 트리 보기에서도 똑같아서 흉내 방식의 한계로 봤다. **끈 뒤 바로 누르기는 실제 기기에서 확인해야 한다.**

### 시안과 견주기

| | 시안 | 시제품 |
|---|---|---|
| 색 조합·여백·절제 | 크림·흑·장미 | 정원에서 같은 인상. 밤은 검은 무대의 다른 분위기 |
| 글자 위계 | 다섯 단계 | 같은 다섯 단계(+ 영상 제목 작은 줄), 모두 12px 이상 |
| 레일·쪽 번호·넘김 | 원형 레일, 휠·끌기·밀기 | 같은 구조. 넘김은 덜 출렁이고 한 칸 = 한 장 |
| **주인공의 힘** | 배경이 지워진 전신 그림이 화면 높이의 70% | **못 미친다.** 네모 썸네일이 틀에 걸린 모습이다. 세로 영상·세로 사진은 꽤 가깝고, 가로 영상(특히 작은 썸네일)은 약하다 |
| **흑백 통일감** | 모든 장면이 흑백 + 색 하나 | **못 미친다.** 유튜브 썸네일은 색 그대로라 장면마다 색이 다르다. 올린 사진 장면만 시안과 비슷하다 |
| 질감 | 종이 입자, 아래 지형 띠 | 없음(테마 층에서 따로) |
| 휴대폰 | 글이 받침과 겹침, 글자 7~8px | 겹침 0, 12px 이상 |
| 미디어 뷰어 | 그림 + 글 + 단추 | 같은 구성의 순간 상세. 재생은 공용 크게 보기 |

요약하면, **틀(색·위계·레일·조작)은 시안만큼 나오고 접근성은 더 낫다. 작품 자체의 힘은 시안에 못 미친다.** 그 차이는 디자인이 아니라 자료(배경 없는 흑백 전신 그림 ↔ 색 있는 네모 썸네일)에서 온다.

### 가장 어려운 점 세 가지

1. **썸네일 품질** — 큰 썸네일(`maxresdefault`)은 없는 영상이 있다(오래된 영상 하나의 그림 주소로 실제 확인: `maxresdefault`·`sddefault` 는 404, `hqdefault`·`mqdefault` 만 있음). `hqdefault` 는 위아래 띠를 빼면 480×270이라 1.35배(648px)까지만 키웠다. 그래도 1440에서 살짝 부드럽다. 세로 영상의 원본 비율 그림이 없으면 가로 그림의 가운데를 잘라 쓴다. 이번 캡처는 대역 그림이라 **실제 썸네일의 선명도는 미리보기에서 실제 계정으로 봐야 한다.** 공유·예시에서는 자동 표시 규칙 때문에 영상 순간이 모두 글 전시물이 된다.
2. **흑백 처리** — 유튜브 썸네일에는 흑백을 걸 수 없고(이슈 규칙), 올린 사진에만 건다. 그래서 한 트리 안에서 색 썸네일과 흑백 사진이 섞인다. 시안의 '흑백 대상 하나 + 포인트 색 하나'는 지금 규칙 안에서는 낼 수 없다. 고를 수 있는 길은 ① 지금처럼 사진만 흑백 ② 모두 색 그대로(통일) ③ 썸네일 효과를 유튜브 준수 심사로 확인한 뒤 적용, 그리고 배경 지우기(조각상 효과)는 이슈 2단계의 일이다.
3. **레일 성능** — 위 수치는 PC 헤드리스 값이다. CPU 를 6배 느리게 걸면 평균 21~24ms 로 내려가고 34ms 넘는 프레임이 14~22개(약 580개 가운데) 나온다. 장면 사이가 한 화면이라 넘길 때 큰 그림 두 장이 함께 움직인다. 레일 점은 지금 순간 수만큼 단추를 만들고 보이는 것만 켠다 — 수백 개 트리에서는 점도 보이는 것만 만들어야 한다. 휠 한 칸 = 한 장 묶음이 터치패드 관성(긴 밀기가 여러 장으로 넘어감)에서 어떤 느낌인지도 실제 기기에서 봐야 한다.
